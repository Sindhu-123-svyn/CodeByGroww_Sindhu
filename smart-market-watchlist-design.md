# Smart Market Watchlist — Design Document

> A watchlist's job isn't to display prices — it's to answer *"what do I need to know since I last looked?"* in under 5 seconds. Everything below is derived from that single thesis.

---

## 1. Product & Problem Interpretation

### 1.1 The gap in the "obvious" watchlist
A standard watchlist is a table of tickers + current price. It answers *"what is the state of the world right now"*. It does not answer the question users actually have when they return to an app: *"what happened while I was gone, and does it matter?"*

That reframing changes the unit of value from **price** to **delta relative to a personal baseline** (the user's last visit), and from **raw numbers** to **ranked significance**.

### 1.2 Core entities
| Entity | Purpose |
|---|---|
| `User` | Owns one or more watchlists. |
| `Watchlist` | Named collection of symbols. |
| `WatchlistItem` | A symbol inside a watchlist, with its own `last_viewed_at` cursor. |
| `PriceTick` | Raw ingested market data point (symbol, price, volume, timestamp, source). |
| `SymbolBaseline` | Rolling statistics per symbol (avg volume, volatility/stddev, 52w high/low) used to judge "meaningful". |
| `ChangeEvent` | A computed, classified, scored deviation for a symbol, generated by the detection layer — this is the object the UI actually renders. |

### 1.3 What counts as a "meaningful change"
Flat thresholds (e.g. "±5%") are naive — 5% is noise for a volatile small-cap and a shock for a stable blue chip. Meaningfulness is computed **relative to the symbol's own behavior**, then classified into types so the UI can explain *why* something surfaced, not just *that* it did.

| Change type | Trigger logic | Why it's meaningful |
|---|---|---|
| **Price Shock** | `\|Δprice\| / rolling_30d_stddev > 2.0` (z-score based, not flat %) | Adjusts for each stock's normal volatility |
| **Volume Anomaly** | `volume > 2× avg_20d_volume` | Unusual volume often precedes/confirms real news, independent of price |
| **Trend Break** | Price crosses 52-week high/low, or crosses its own 20-day moving average | Structural signal, not noise |
| **Gap Event** | `\|open_today − prev_close\| > 1.5× rolling stddev` | Captures overnight/pre-market moves the user missed entirely |
| **Data Quality Flag** | Stale (> N minutes old), source conflict, or missing tick | Not a market signal — a trust signal. Surfaced separately so it's never confused with a real price move. |

Each `ChangeEvent` gets a **severity score** (not just a boolean), so the UI can rank a user's whole watchlist by "what deserves attention first" instead of listing 20 tickers in alphabetical order.

### 1.4 Since-last-visit framing (the actual differentiator)
Every `WatchlistItem` stores `last_viewed_at`. On load, the backend queries all `ChangeEvent`s for that symbol with `event_time > last_viewed_at`, not "since yesterday's close." Two users opening the same watchlist at different times see **different** deltas from the same underlying data — because the product is answering *their* question, not a global one. `last_viewed_at` only advances when the user explicitly acknowledges the digest (not on every page load), so a quick glance doesn't silently swallow a signal they didn't actually register.

## 2. Engineering Depth — Architecture, Correctness, Reliability, Scalability

### 2.1 High-level architecture

```
                 ┌─────────────────────┐
                 │   Market Data APIs   │  (external, unreliable)
                 └──────────┬───────────┘
                            │
                 ┌──────────▼───────────┐
                 │   Ingestion Worker    │  polls on a schedule,
                 │  (decoupled process)  │  normalizes ticks, tags source
                 └──────────┬───────────┘
                            │ writes
                 ┌──────────▼───────────┐
                 │   Price Cache/Store   │  latest tick per symbol
                 │  (shared, not per-user)│  + historical ticks for baselines
                 └──────────┬───────────┘
                            │ triggers
                 ┌──────────▼───────────┐
                 │  Change Detection Job │  computes rolling stats,
                 │  (separate from API)  │  classifies + scores ChangeEvents
                 └──────────┬───────────┘
                            │ writes
                 ┌──────────▼───────────┐
                 │     ChangeEvent DB    │
                 └──────────┬───────────┘
                            │ reads (cheap, precomputed)
                 ┌──────────▼───────────┐
                 │    FastAPI (REST)     │  watchlist CRUD, digest endpoint,
                 └──────────┬───────────┘  auth, last_viewed_at cursor
                            │
                 ┌──────────▼───────────┐
                 │   React Frontend      │  "what changed" as hero view
                 └───────────────────────┘
```

**Key architectural decision: separate ingestion, computation, and serving into three processes.** This is the difference between a toy CRUD app and a system that scales:
- The API layer never talks to external market data directly — it only reads precomputed state. This keeps API latency flat regardless of how expensive change-detection math is.
- The ingestion worker fetches **once per symbol**, not once per user-watchlist. A symbol held by 10,000 watchlists is still fetched once. This is the single biggest scaling lever in the whole system.
- Change detection is a pure function of `(new tick, symbol baseline) → ChangeEvent`, independent of any specific user, so it scales with *number of symbols tracked platform-wide*, not *number of users*.

### 2.2 Data model correctness
- `PriceTick` is **append-only** (never mutated) — this makes baseline recomputation, backfills, and audits trivial, and means a bad tick can be quarantined without corrupting history.
- `ChangeEvent` generation is **idempotent**: keyed on `(symbol, event_type, event_time)`, so re-running the detection job (e.g. after a crash) never double-emits the same event.
- `last_viewed_at` is per `(user, watchlist_item)`, not global per symbol — correctness requires this, since the same symbol can be "new" to one user and "already seen" to another.

### 2.3 Reliability
- Ingestion and detection are **independently retryable** background jobs — a failure in one doesn't take down the API or the other job.
- The API layer degrades gracefully: if the change-detection job is behind, the API serves the last-known `ChangeEvent`s with a visible "as of" timestamp rather than blocking or erroring.
- All external API calls have timeouts + exponential backoff + a circuit breaker so one flaky provider can't cascade into a full ingestion outage.

### 2.4 Scalability
| Dimension | Bottleneck if naive | Design response |
|---|---|---|
| More users, same symbols | Redundant API calls per user | Shared price cache keyed by symbol; users just subscribe to it |
| Larger individual watchlists | Detection recompute cost grows per symbol | Detection is already symbol-scoped, not watchlist-scoped — no extra cost per additional user watching a symbol |
| More total symbols platform-wide | Ingestion worker becomes the bottleneck | Horizontally shard the ingestion worker by symbol range; each shard owns a partition of the symbol space |
| Read-heavy digest endpoint | DB hit on every page load | `ChangeEvent`s are precomputed and small — cache the "current digest" per symbol in a fast store (e.g. Redis) with short TTL, invalidated on new event write |
| Real-time expectations | Polling doesn't scale to per-second updates for thousands of clients | v1 uses polling (simple, sufficient); documented upgrade path to WebSocket/SSE push for `ChangeEvent`s only (not raw ticks) — push the *signal*, not the *noise* |

## 3. Edge Cases & Resilience

This is the section most "obvious watchlists" skip entirely — treating it as a first-class design concern rather than a try/catch afterthought.

### 3.1 Stale data
- Every price shown carries an explicit **freshness indicator** (`updated_Xs_ago`), never silently presented as live.
- Past a staleness threshold (e.g. 5 min during market hours), the UI visually grays the value and the backend excludes it from `ChangeEvent` generation — a stale price cannot trigger a false "shock" alert.

### 3.2 Delayed / missing ticks
- A gap in the tick stream (e.g. provider outage) is detected by the ingestion worker (expected-tick-not-received) and logged as a `DataQualityFlag`, not silently ignored.
- Change detection treats a gap as "insufficient data" rather than interpolating a fake price — no invented signal.

### 3.3 Conflicting data sources
- If a symbol is ever backed by >1 provider, each tick is tagged with its source and a trust priority (e.g. exchange-official > aggregator).
- If two sources disagree beyond a tolerance, the system does **not** silently pick one — it surfaces the divergence itself as a `DataQualityFlag`, since disagreement between sources is information the user may want ("data currently uncertain") rather than something to paper over.

### 3.4 Market closed / off-hours
- Change detection is aware of market-hours calendars per exchange; it doesn't classify the overnight non-move as "no change" — instead it evaluates the **open gap** the next session as a distinct `GapEvent` type (see §1.3), since that's exactly the kind of change a user would otherwise miss entirely between visits.

### 3.5 New symbol / no baseline yet
- A symbol just added to a watchlist has no rolling stats yet. The system explicitly shows "building baseline — insights available after N days" rather than either crashing or falsely reporting "no meaningful change" (which would be a lie, not a null result).

### 3.6 Corporate actions (splits, dividends)
- A raw price change from a stock split would otherwise register as a massive false "Price Shock." The ingestion layer applies split/dividend adjustment factors before feeding the detection layer, so mechanical price jumps are never confused with market-driven ones.

### 3.7 Race conditions
- Concurrent writes to `last_viewed_at` (e.g. same user on two devices) are resolved with a simple **last-write-wins on advance only** rule — the cursor only ever moves forward, never backward, so a race can at worst mark something as seen slightly early, never lose an unseen event forward in time incorrectly.
- Change-event writes are idempotent (see §2.2), so concurrent detection job runs can't duplicate events.

### 3.8 Abuse / scale edge cases
- Per-user rate limits on watchlist size (with a sane default, upgradeable) to prevent a single user from degrading the shared ingestion budget for everyone.
- Symbol validation on add (reject unknown/delisted tickers early with a clear error, not a silent empty state later).

## 4. Code Quality & Simplicity

Principles applied throughout, not just stated:
- **Single-responsibility services**: ingestion, detection, and API are separately deployable and separately testable — no shared mutable state between them beyond the DB/cache.
- **Pure computation for the hard part**: change classification is a pure function `(tick, baseline) → ChangeEvent | None` — easy to unit test exhaustively with synthetic data (shocks, gaps, missing data, split days) without needing a live market feed.
- **No premature complexity**: no message queue, no microservice mesh, no multi-region deployment for v1 — a single scheduled job + REST API is enough to prove the model correctly; the scaling section above documents *where* it would need to change, without building that infrastructure speculatively.
- **Explicit over implicit**: freshness, confidence, and "why this event fired" are always modeled as visible fields, never hidden in comments or inferred by the frontend.

## 5. Originality & Thoughtfulness — Summary of Independent Choices

1. **Reframing the product** from "current state" to "delta since last visit," with the cursor stored per user, not globally — this is the single choice everything else follows from.
2. **Volatility-relative significance** (z-scores against a symbol's own rolling stats) instead of flat percentage thresholds — avoids both alert fatigue on volatile names and missed signals on stable ones.
3. **Treating data quality as a first-class, user-visible state** (freshness, source conflicts, gaps) rather than an internal error to hide.
4. **Corporate-action adjustment** before detection, so mechanical price changes (splits) never masquerade as market signals — an easy-to-miss but important correctness detail.
5. **Decoupling ingestion from watchlist count** — the architecture cost scales with *distinct symbols tracked platform-wide*, not with *users × symbols*, which is the actual scaling constraint that matters for a watchlist product.
6. **Explicit deferral of real-time push**, with a stated rationale (push signals, not raw ticks) — shows the "simple now, considered path to complex later" judgment the brief asks for, rather than either over-building or ignoring the question.

## 6. What's Deliberately Out of Scope for v1 (and why)

| Cut | Reason |
|---|---|
| Multi-exchange, production-grade data licensing | Orthogonal to the product problem being solved; a mock/free data feed is sufficient to prove the change-detection model |
| Full OAuth/SSO | Interesting problem, not *this* problem; minimal auth is enough to demonstrate per-user state |
| WebSocket push | Adds infra complexity before the polling model has even been validated; documented as the clear next step |
| ML-based anomaly detection | Statistical (z-score) methods are explainable — a user can see *why* something fired, which matters more than marginal detection accuracy for a v1 |
